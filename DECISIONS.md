# DECISIONS.md

1. **Indexes.** In the `employees` collection, I made a unique index on `emp_code` so two employees cannot have the same code, and it also helps in sorting. In `attendance_logs`, I made a unique index on `(emp_code, date)` so an employee can only punch in once per day, and it makes searching by employee and date fast. I also added an index on `(emp_code, punch_in)` to quickly find the last punch-in time during punch-out. I did not make an index on `status` because it has only 5 fixed values.

2. **Punch-in race.** If two same punch-in requests come at the exact same time, both check the employee and try to run `insert_one` directly. Because of the unique index on `(emp_code, date)`, MongoDB allows only the first request to save and gives `201`. The second request gets a `DuplicateKeyError`, which my `try-except` block catches and returns as a `409` error.

3. **Ties.** In the late leaderboard, if I simply used `$limit`, it would cut off employees who have the exact same `total_late_minutes` at the boundary. Instead, I used MongoDB's `$setWindowFields` with the `$rank` operator sorted by `total_late_minutes` descending. This gives standard competition ranking (for example, if two people tie for 2nd place, both get rank 2, and the next person gets rank 4). After assigning ranks, I used `$match: {"rank": {"$lte": limit}}` instead of `$limit`. So if `limit` is 10 and two employees are tied at rank 10, both of them are returned in the response (making 11 rows total), sorted by `total_late_minutes` descending and then `emp_code` ascending.

4. **Headcount.** An employee can belong to a department and have joined on or before the end of the month, but still have zero records in `attendance_logs` (for example, if they never punched in). If we start the aggregation pipeline on `attendance_logs`, those employees will be completely missed and the department headcount will be wrong. To fix this, the pipeline must start on the `employees` collection, filter employees where `joined_on` is less than or equal to the last day of the month, and then use `$lookup` (which works like a LEFT JOIN) to attach matching logs from `attendance_logs`. Even if an employee's looked-up logs array is empty, that employee is still counted in the department's `headcount`.

5. **One thing you would change.** Right now, the analytics endpoints scan and group raw documents from `attendance_logs` on every API call. If the data grows by 100x, running aggregations over millions of daily logs on every request will become very slow and heavy on CPU and RAM. To handle 100x scale, I would create a separate pre-aggregated collection (like `monthly_employee_summaries` and `daily_department_stats`). Whenever an employee punches in, punches out, or gets regularized, the API would immediately update their monthly totals (`present_days`, `total_late_minutes`, `overtime_minutes`) using `$inc`. Then the analytics endpoints can simply read those pre-calculated summary documents in milliseconds without scanning the raw logs.
